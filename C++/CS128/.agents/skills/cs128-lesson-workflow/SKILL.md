# CS 128 Lesson Workflow

Use this skill when the user gives a CS 128 lesson URL and asks to make notes, prepare its programming activity, solve it, and submit/grade it.

## Workflow

1. **Open the lesson.** Follow the user's browser preference. If none is stated and browser navigation is needed, ask whether to use the in-app browser or Chrome, then use their choice. Read the lesson headings, core explanations, and the full Programming Activity specification, including constraints and starter-file structure.
2. **Make a concise lesson folder.** In the user's existing CS 128 notes directory, copy the established `L1 Hello World` folder as the template. Name the new folder `L<number> <Lesson Name>` (infer the next lecture number from the existing sequence). Remove the copied Hello World source file, rename the copied notes file to match the new lesson, and keep the template's folder conventions. Reuse the shared `Lecture Notes/Makefile` by making each lesson folder Makefile contain `include ../Makefile`; do not copy a custom build recipe unless the user asks. Keep the lesson folder minimal: do not copy `.devcontainer/`, `.vscode/`, `.clang-format`, `.clang-tidy`, or other editor/container/linter settings unless the user explicitly requests them. Remove build products such as executables and `.dSYM` bundles; retain only source, notes, problem text, and needed directory placeholders.
3. **Write notes in the user's format.** In the notes file, retain the lesson's original content subsection titles, but omit `Learning Objectives` and `Programming Activity` as note sections. Match the established L36/L37 hierarchy: lesson title at the left margin, subsection titles indented four spaces, key English sentences indented eight spaces, and code examples indented twelve spaces. Use short English sentences, one per line, without bullets or numbering. Prefer key textbook wording with light trimming and include only essential code. In the chat, explain the lesson in Chinese, organized by every original content subsection. Cover each subsection's main idea and its connection to the lesson; use a short code example, trace, or diagram where useful. Avoid retelling every sentence or routine activity/output. Explain the Programming Activity separately in Chinese: clarify its data representation, required operations, constraints/invariants, and how it connects to the lesson. Then provide the English notes.
4. **Preserve the assignment locally.** Copy the full Programming Activity prompt into `src/problem.txt`, including its introduction, struct/member descriptions, provided function signatures and descriptions, function to implement, ordered steps, memory-management rules, constraints, and starter-file list. Do not summarize or omit parts of the specification. Omit page metadata that is not part of the problem statement, specifically labels such as `Graded Playground Autograder` and due dates/times. Preserve the activity title and assignment requirements. Download all provided `.cc` and `.hpp` starter files into the matching `src/` and `includes/` folders. Preserve supplied files and their interfaces.
5. **Implement carefully.** Work through the specification and edge cases; compile locally with the exact course C++ standard and warning flags when available. Keep the implementation readable and satisfy style/lint conventions as well as functional tests. For graded coursework, support the user's learning by explaining the key invariant and reasoning instead of hiding the solution process.
6. **Submit and iterate.** Upload the completed project to the correct course activity, run it if needed, then click Grade. Read every failed rubric item and diagnostic, fix it locally, upload the updated files, and grade again. Do not stop at a successful compile, a high score, a queued job, or an assumed result. Wait for the grader to finish and verify the latest result explicitly says `GRADED (100%)` and all rubric items pass. If the grader is still running, continue checking; report a blocker only when a concrete external problem prevents progress.
7. **Clean, commit, and publish the work.** Remove copied editor/container/linter configuration and compiled artifacts from the new lesson folder unless explicitly requested. Inspect `git status`, confirm the configured remote and branch, and stage only the intended lesson folder and this skill. Follow the repository’s established commit style: make one commit for the lesson, with a specific title in the form `commit L<number> <Lesson Name>` (for example, `commit L37 Arrays Under the Hood`). Avoid abstract generic titles or conventional prefixes such as `docs:` and `fix:` when the repository uses its lesson-title format. Include the skill update in the lesson commit when it belongs to that lesson. **For every run triggered by the scheduled CS128 automation, always push the completed lesson commit to the existing repository remote after grading reaches 100%; this standing instruction does not need to be repeated in that run.** For interactive runs outside that automation, push only when the user explicitly requests it. Before pushing, review the intended commit and remote/branch; afterward verify the remote branch contains the commit and the local branch is up to date. If no remote is configured or push fails, report the concrete blocker.
8. **Close with a compact explanation.** Explain the central content of every subsection in Chinese with enough detail for the user to follow the lesson’s reasoning. Add small code examples, traces, complexity notes, or a diagram where useful. Keep the explanation clear and substantially shorter than the source lesson, while covering each subsection; do not compress it to one headline or an overly brief summary. Explain the Programming Activity and its connection to the lesson’s core idea. Report the final grade only after verifying 100%, and link the local notes and solution files.

## Completion checklist

- [ ] Lesson folder follows the local template and naming convention.
- [ ] Notes file uses original subsection headings and the requested English line format.
- [ ] `problem.txt` contains the assignment requirements.
- [ ] All starter `.cc` and `.hpp` files are present in the project.
- [ ] Implementation satisfies the specification and compiles with course flags.
- [ ] The lesson Makefile includes `../Makefile`, and no unwanted template configuration or build products remain in the lesson folder.
- [ ] Lesson commit follows the established title format; scheduled CS128 automation runs are pushed to the configured remote and verified.
- [ ] Course page shows the latest result as `GRADED (100%)`.
- [ ] Final response gives a concise Chinese explanation and links the artifacts.

## Reflection gates

- The user reports two ways the current course can release a reflection gate: actively write and revise in the response for more than 60 seconds, or complete all five graded attempts. Treat these as user-observed behavior and verify the actual page state each time.
- Follow the displayed duration when it is longer (the previous lesson included 90-second prompts). Use the time to review and shorten the answer, keeping all requested points and the displayed word minimum. The user prefers direct answers without filler.
- Save after the required time, inspect feedback, and revise meaningfully before another attempt. Use the attempt limit actually displayed by the page (Introduction to Graphs displayed three, not five). If exhausting that limit permits continuation, use its Continue control. Stop attempts once the gate is complete. Do not assume a save or elapsed time alone unlocked it.
- After a successful reflection, use Continue. If the saved grade is complete but content remains locked, reload the page and inspect the newly available section.
